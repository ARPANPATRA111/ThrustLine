## 1. The game in one minute

THRUSTLINE is a real-time, side-view jetpack shooter that runs in the browser on phones and
laptops. Players press Quick Play to join a public match, or 1–8 friends share a room through a
4-letter code or an invite link. They fight on two maps, RIG-7 and HELIOS-9, either free-for-all or
as red vs blue teams, for kills or for a moving hill. Players run, fly with an analog jetpack,
shoot hitscan guns, throw bouncing grenades, grab health, ammo, shields and railgun airdrops, and
avoid the acid. A round lasts 2–10 minutes; the last minute is "Frenzy" (more damage, faster fuel)
and in the last 30 seconds the acid rises. The highest score (or team total) wins. Finished rounds
pay XP towards levels, sticker unlocks and a monthly season board.

Technically it is three parts written in one language, TypeScript:

- a **browser client** (PixiJS for graphics, plain DOM for menus, Web Audio for sound),
- a **game server module** running inside **SpacetimeDB**, a database that also runs server code,
- a **shared simulation** folder (physics, map, raycasts, grenades, rules) used by both.

There is no sign-up: progress lives on an anonymous identity saved in the browser. A dropped player's
slot is held for 30 seconds. All art and sound are generated by code when
the page loads; nothing is downloaded except two open-licence fonts bundled with the app.

## 2. What the player sees and does

**Screens**: loading → home (callsign, Quick Play, create/join, how to play, season board, settings)
→ lobby (room code, invite link, players, host settings; Quick Play skips it) → game (HUD, touch
controls) → round over (results, countdown) → back to the lobby, or straight into the next round in
Quick Play. Overlays: respawn screen with kill recap and weapon choice, scoreboard, pause menu,
settings, rotate-your-phone prompt.

**Controls**

| Action | Keyboard & mouse | Touch (landscape) |
| --- | --- | --- |
| Move | A / D | Left stick, horizontal |
| Jetpack | W / Space (tap = hop, hold = fly) | Left stick up, analog: gentle push hovers, further climbs |
| Drop through a platform | S | Left stick pulled firmly straight down |
| Aim / fire | Mouse / left click | Right stick direction / push past ~55 % |
| Knife, grenade, swap, reload | R or right click, G, F, T | Buttons on an arc around the right stick |
| Emote | Q, or the button beside the leaderboard; 1 to 4 send a favourite sticker | Button beside the leaderboard |
| Scoreboard / menu / stats | Tab / Esc / F3 | Tap mini leaderboard / ≡ button / Settings |

Every key can be rebound in Settings, and gamepads work on the standard layout (`game/input.ts`).

**HUD**: health and fuel bars with a shield strip, minimap, timer (turns into a red FRENZY badge), team score bar
(team matches), ping and FPS chip, mini leaderboard with everyone's ping, kill feed with weapon
icons, weapon and ammo panel, crosshair, hit markers, damage vignette and direction arc, edge
arrows toward off-screen enemies who are shooting.

## 3. Architecture at a glance

```text
 Phone / laptop browser (one per player)                       SpacetimeDB server
 ┌─────────────────────────────────────────────┐              ┌──────────────────────────────┐
 │ UI (DOM + CSS)   HUD, menus, touch controls │              │ THRUSTLINE module (index.ts) │
 │ Game loop 60 Hz  your soldier simulated     │  sync 20 Hz  │  reducers = the referee      │
 │   locally ("prediction")                    │ ───────────▶ │  - validate movement/shots   │
 │ Remote players drawn slightly in the past   │              │  - apply damage, score, ammo │
 │   ("interpolation")                         │ ◀─────────── │  - timers: respawn, round,   │
 │ PixiJS renderer (WebGPU/WebGL)              │  row updates │    grenades, pickups         │
 │ Web Audio (synthesised sounds)              │  + events    │ tables = the game state      │
 │ CPU bots (optional, hosted in this tab)     │  (WebSocket) │  room, player, pstate, ...   │
 └──────────────┬──────────────────────────────┘              └──────────────┬───────────────┘
                │            shared/  (pure TypeScript)                       │
                └──────────  physics · map · raycast · grenade · spawn  ──────┘
                             validate · weapons · config · names
```

**Authority model ("the server is the referee")**: each client simulates its *own* soldier and
reports position, shots, knife swings and throws. The server checks every report against the
rules (no teleporting, no walls in the way, no shooting faster than the gun allows, no hitting
someone out of range or behind cover) and owns everything that decides the match: HP, deaths,
kills, score, ammo, pickups, grenades, spawns, teams and the clock.

**Data flow**: the server stores the game as database **tables**. Clients **subscribe** to the
rows of their own room. When a reducer changes rows, SpacetimeDB pushes the changed rows to every
subscribed client over a WebSocket. One-off happenings (a shot, a hit, a kill, an explosion) are
sent through **event tables**: rows that are broadcast once and never stored.

## 4. Technology stack and why each piece was chosen

| Layer | Choice | Why this | Alternatives considered |
| --- | --- | --- | --- |
| Language | **TypeScript** (strict), everywhere | One language for client, server and the shared physics, so the exact same collision and grenade code runs on both sides. Type checking catches bugs before running. | JavaScript (no types), C#/Unity (heavy download, not one codebase with the web UI) |
| Rendering | **PixiJS v8** | Fast 2D sprite batching; WebGPU where available, WebGL elsewhere; small. We only need sprites, not a full engine. | Phaser (bundles its own physics and scene system we don't need), raw WebGL (too much code), Canvas 2D (too slow for many sprites on phones) |
| UI | **Plain DOM + CSS** | Crisp text, accessible buttons, tiny bundle; HUD writes only when a value changes. | React (per-frame virtual DOM work, bigger bundle) |
| Physics | **Custom** (~200 lines) | A platformer needs simple box-vs-tile collision, one-way platforms and a jetpack. It must be deterministic and identical on client and server. | Matter.js / Box2D (rigid-body physics we don't want; harder to make identical on the server) |
| Audio | **Web Audio API**, sounds synthesised in code | Low latency, no audio files to download, meets the "self-made assets" rule. | Howler.js + audio files |
| Backend | **SpacetimeDB 2.x** TypeScript module | Database and server in one: tables, server functions (reducers), real-time subscriptions, timers (scheduled reducers) and event broadcast are built in. No separate web server, no REST API, no cache layer to write. | Node.js + Socket.IO + Redis (we would write state sync, persistence and timers ourselves), Firebase (not designed for 20 Hz game state; no server-side validation of physics), Colyseus (a game server, but a separate service to host) |
| Client SDK | **`spacetimedb` npm package** + generated bindings | Typed tables and reducer calls generated from the server code: a renamed field fails to compile instead of failing at runtime. | Hand-written WebSocket protocol |
| Build | **Vite** | Instant dev server, static `dist/` output | Webpack |
| Hosting | **Vercel** (client), **SpacetimeDB Maincloud** (server; a free India server is prepared, see section 19) | Free static hosting with HTTPS and a CDN; managed database server | Netlify, GitHub Pages |
| Tests | **Vitest** (unit), **Playwright** (real multi-browser games) | Fast unit tests for the simulation; end-to-end tests that open several real browsers and play | Jest, Cypress |
| Fonts | Russo One, Chakra Petch (OFL licence, npm `@fontsource`) | Game-like look, bundled locally (no third-party CDN) | System fonts |

**Why one shared simulation folder matters**: the client must predict its own movement instantly
(no waiting for the server), and the server must check that movement. If they used different
physics, every legal move could look illegal. Sharing `server/src/shared/` guarantees they agree.
It lives inside the server folder so SpacetimeDB's bundler includes it; the client imports it
through the `@shared` alias.

## 6. The game loop and rendering

### Fixed-timestep loop (`client/src/game/game.ts`, `frame()`)

Screens refresh at 60, 90 or 120 Hz and frames take uneven time, but physics must behave the same
for everyone. So the loop uses an **accumulator**:

```text
acc += time since last frame (capped at 0.1 s)
while acc >= 1/60:  step the simulation exactly 1/60 s;  acc -= 1/60
alpha = acc / (1/60)
draw everything at  previous + (current − previous) × alpha
```

The simulation always moves in identical 1/60 s steps (deterministic, frame-rate independent);
drawing blends the last two steps so motion is smooth at any refresh rate. A one-off press (click,
grenade key) is applied to exactly one step. The 0.1 s cap stops a frozen tab from fast-forwarding.

### Rendering (PixiJS)

- **One texture atlas**: every sprite (soldier parts, guns, effects, pickups, icons) is drawn with
  Canvas 2D at load into one 2048×2048 canvas, packed with a shelf packer, and uploaded once. All
  sprites share one texture, so the GPU draws them in very few batches (`render/atlas.ts`).
- **Baked map**: RIG-7 (96×40 tiles of 32 px = 3072×1280 px) is drawn once into six 1024 px
  textures. The whole static map costs six sprites per frame instead of 3,840 tiles
  (`render/mapbake.ts`).
- **Parallax**: three backdrop layers move at 0.15, 0.4 and 0.7 of the camera speed for depth.
- **Object pools**: particles (400 max), tracers, flashes and damage numbers are created once and
  reused; nothing is allocated per frame, so the garbage collector doesn't cause stutters.
- **Soldiers are animated in code**: legs swing with speed, the body bobs, the arm and gun rotate
  to the aim angle, the jet flame flickers. No sprite sheets (`render/soldier.ts`).
- **Camera**: follows with a 0.12 smoothing factor, leads toward the aim (320 px with the sniper),
  shakes briefly on shots and blasts, clamps to the map, and zooms in on short phone screens
  (view height = screen height × 1.08, between 420 and 680 world px).
- **Quality governor**: if FPS stays under 50 for 3 s, it lowers resolution, then particles, then
  parallax layers; it steps back up after 10 s above 58.

## 7. Movement physics (`server/src/shared/physics.ts`)

The player is an axis-aligned box, 24×48 px. Position is the centre of the feet.

**Each 1/60 s step**: (1) update velocity from input: run acceleration 2400 px/s², air control
1400, ground friction 2600; (2) jetpack and gravity (1800 px/s², max fall 900); (3) **move X,
then Y, separately**, resolving collisions one axis at a time.

**Axis-separated collision**: after moving horizontally, if the box overlaps a solid tile it is
placed flush against that tile and horizontal speed becomes 0; the same for vertical. Speeds are
capped so one step moves less than half a tile, so checking the destination edge is enough and
the player can't tunnel through walls.

**One-way platforms** (`=` in the map, drawn as see-through mesh catwalks): they only matter when
moving down, and only block if the feet were at or above the platform's top before this step and
"down" isn't held. Jumping up from below, the feet start under the top, so you pass through and
then land on it. Holding down ignores them, so you drop through.

**Analog jetpack (Mini Militia style)**: thrust power 0–1 (touch stick: how far up you push;
keyboard: full). Upward force = 3000 × power px/s². Gravity is 1800, so power 0.6 (= 1800/3000)
exactly cancels gravity: hover. While the jets fire, vertical speed is also damped
(`vy −= vy × 2.5 × dt`, applied after gravity so hover is exact), which makes hovering and flying
sideways at one height easy to hold. A tap on the ground is a hop (−520 px/s, 6 fuel). Fuel: 100,
drains while flying (scaled by power), refills 60/s after 0.15 s on the ground (about 1.7 s from
empty to full).

**Impulses**: shotgun recoil (520), knife lunge (220) and grenade knockback (up to 650) push the
player ("blast-jumping"), capped at 1000 px/s sideways.

## 8. Combat

### Guns are hitscan (`client/src/game/actor.ts`, `fire()`)

A shot is a ray, not a flying bullet. For each pellet:

1. **DDA grid walk** (`castTiles`): from the gun, step tile by tile along the ray, always into
   whichever grid line (vertical or horizontal) is closer, until a solid tile. Cost is
   proportional to the tiles crossed, and it never misses a tile. Gives the wall distance.
2. **Slab test** (`rayVsBox`) against every other player's hitbox: a box is the overlap of an
   x-band and a y-band; compute where the ray enters/leaves each band; it hits if the latest entry
   is before the earliest exit and before the wall.
3. The nearest hit wins. The client draws the tracer immediately and sends a **hit claim**
   (target, pellets, ray angle, and when it saw the target) in the next sync. Damage only appears
   when the server confirms it (`hit_ev`).

| Weapon | Damage | Rate | Notes |
| --- | --- | --- | --- |
| Pistol | 18 | 4/s | always carried, infinite reserve |
| AR | 11 | 10/s | automatic; more spread while moving |
| SMG | 8 | 14/s | fast and forgiving; falls off past 450 px |
| Shotgun | 10 pellets × 10 | 1.3/s | all pellets at point blank; falls off past 200 px (55% at 460); recoil |
| Sniper | 100 | 0.85/s | one clean body hit kills; no spread when still |
| Knife | 55 | 2/s | server finds targets: within 72 px and ±70° |
| Frag | up to 100 | — | 1.5 s fuse, bounces, linear falloff to 0 at 170 px, half on yourself |
| Railgun | 150 | 0.9/s | airdrop only, 3 shots, pierces bodies but not walls |

### Grenades are deterministic (`server/src/shared/grenade.ts`)

When a grenade is thrown, the server stores only its start position, velocity and throw time.
The server and every client run **the same simulation** on those same numbers: fixed 120 Hz
steps of gravity, bounces (restitution 0.45, friction 0.7), landing on platforms, rolling to rest.
It uses only + − × ÷ and comparisons (no sin/cos, no randomness), which give identical results on
every device. So the explosion happens exactly where everyone saw the grenade, without streaming
its position. The client precomputes the whole path once and looks it up each frame.
**Floating grenades** (house rule): the same simulation with gravity off and a 0.99 drag factor
per step, so grenades drift where thrown and slow to a stop in mid-air.

## 9. Multiplayer networking (the core of the project)

### 9.1 The sync message

Every 50 ms while active (200 ms when idle) each client calls the `sync` reducer with: its
position and velocity, aim, weapon, a timestamp `t`, a sequence number, its life id, its
correction counter, and any queued actions (shots with hit claims, knife swing, grenade throw,
reload).

### 9.2 What the server does with a sync (in order)

1. Ignore it if the player isn't alive in a playing room, or it's from a previous life.
2. **Movement check**: the new position must be inside the map, not inside a wall, and no farther
   than `1400 px/s × dt × 1.3 + 24 px` from the last accepted position. If it fails, the server
   increments the player's `correction` counter and the client snaps back.
3. Finish a reload if its time has passed.
4. Acid damage (30 HP/s) if the hitbox touches acid.
5. Pickups the player is touching.
6. Actions: weapon switch, reload, each shot (validated, below), knife, throw.

### 9.3 Client-side prediction (your own soldier)

Your soldier moves the instant you press a key: the client runs the shared physics locally and
never waits for the server. The server's copy is only used to correct you when it rejects a move
(correction counter goes up → snap to the server's last good position) or when you respawn.

### 9.4 Interpolation (everyone else) with adaptive delay (`client/src/net/interp.ts`)

Other players' positions arrive ~20 times a second, unevenly. Each update is stored in a 20-entry
**ring buffer**, stamped with the time it was simulated on the *sender's* clock (`sentMs`). Each
frame, every remote player is drawn a little in the past, interpolating between the two
snapshots around that time (position linearly, aim the short way round the circle).

How far in the past? A fixed 100 ms only works on a fast network: at 250 ms ping an update is
already 120–250 ms old when it arrives, so the game would always be guessing ahead and snapping
back. So each remote player has a **LagEstimator** that measures how late updates arrive
(`lag = serverNow − sentMs`), keeps a running average and jitter, and draws that player
`average + 2 × jitter + 35 ms` in the past. The delay grows quickly and shrinks slowly, so the
drawn timeline never jumps. CPU bots hosted in your own tab are drawn from their exact local
simulation instead (no delay at all).

### 9.5 Clock synchronisation (`client/src/net/timesync.ts`)

Clients need to know the server's time (round timer, grenade paths, interpolation). They send a
`ping` with their local time; the server replies with its time. `RTT = now − sent`;
`offset = serverTime − (sent + RTT/2)`. The median of the last 5 offsets is used, so one slow
packet can't skew the clock. 5 quick pings at start, then one every 2 s. The same message reports
your RTT to the server, which shows everyone's ping on the scoreboard.

### 9.6 Movement checks on the client's timeline (anti-rubber-banding)

On mobile data, two syncs sent 50 ms apart can arrive 5 ms apart. If the server measured movement
against its own 5 ms, fast flying would look like teleporting and be rejected. So the server
measures time between the client's own timestamps. To stop a client from claiming extra time
(a speed hack), the total extra time a client may claim over the server's clock is capped at
350 ms (`timeDebtMs`); beyond that its allowance shrinks.

### 9.7 Hit validation and lag compensation ("favour the shooter, but cover wins")

For each shot the server checks: correct weapon equipped and allowed in this mode, not reloading,
fire rate respected (a token bucket allows two shots bundled into one sync), magazine not empty,
shot origin within 48 px of the shooter. For each claimed target: same room, alive, not
spawn-protected, not a teammate when friendly fire is off; **clear line of sight to the target's
current position** (so once you're behind a wall you're safe); and the claimed ray must pass
within the target's half-diagonal + 40 px of where the target **was when the shooter saw it**.
The server keeps the last 16 positions of each player with timestamps, so a shooter on a slow
connection who aimed correctly on their screen still hits (up to 700 ms back). Damage always
comes from the server's weapon table and the server's distance measurement.

### 9.8 Subscriptions and events

A client subscribes only to its own room (`room`, `player`, `pstate`, `pickup`, `grenade` and the
event tables filtered by `roomId`), plus its own player row, pongs and kick notices. Transient
things use **event tables** (`shot_ev`, `hit_ev`, `kill_ev`, `melee_ev`, `boom_ev`, `pickup_ev`,
`pong_ev`, `kick_ev`): broadcast once on commit, never stored, so nothing piles up.

### 9.9 Bandwidth

Per player: 20 small syncs per second up; per update down ≈ one row per moving player. Movement
(`pstate`) is a separate table from stats (`player`) so a 20 Hz position write doesn't resend
names, scores and ammo.

## 10. The server: tables, reducers, scheduled jobs, events (`server/src/index.ts`)

**SpacetimeDB in one paragraph**: a relational database that also runs your server code. You
define **tables** (the state) and **reducers** (functions clients call to change the state).
Each reducer runs as a **transaction**: all of its changes commit together or not at all, and
reducers run one at a time, so there are no race conditions. Clients **subscribe** to queries and
receive changed rows automatically. **Scheduled tables** run a reducer at a given time.
Randomness and time inside reducers come from the context (`ctx.random`, `ctx.timestamp`) so they
are deterministic.

**Tables**

| Table | Public? | Holds |
| --- | --- | --- |
| `room` | yes | code, host, state (lobby / playing / ended), mode, round length, teams flag, house rules, match options, map, Quick Play flag, round times |
| `player` | yes | name, colour, team, alive, HP, shield, railgun shots, life id, kills, deaths, score, streak, weapon, ammo, timers, correction, ping, connected flag |
| `pstate` | yes | position, velocity, aim, flags, sender timestamp (hot, 20 Hz) |
| `pmeta` | no | anti-cheat bookkeeping: last sync, previous position, fire times, position history, time debt, movement credit, connection id |
| `throttle` | no | per-identity limits on creating rooms, joining and pings |
| `pickup` | yes | crate kind, tile, when it becomes available again |
| `grenade` | yes | owner, start position and velocity, throw time, fuse, zero-g flag |
| `hill` | yes | King of the Hill: live zone, who holds it, when it moves |
| `profile` | yes | **permanent**: XP, lifetime stats, season points |
| `season_board` | yes | **permanent**: top 20 of the current season |
| `kicked` | no | who the host removed from which room |
| `emote_log` | no | per-player emote cooldown |
| `respawn_job`, `round_end_job`, `lobby_job`, `detonate_job`, `pickup_job`, `airdrop_job`, `hill_job`, `drop_job` | no | one-shot timers |
| `shot_ev`, `hit_ev`, `kill_ev`, `melee_ev`, `boom_ev`, `pickup_ev`, `emote_ev`, `pong_ev`, `kick_ev`, `notice_ev` | yes (event) | broadcast-once events |

**Reducers**: `createRoom`, `quickPlay`, `joinRoom`, `leaveRoom`, `kickPlayer`, `updateRoomSettings`,
`switchTeam`, `movePlayerTeam`, `backToLobby`, `startRound`, `choosePrimary`, `emote`, `ping`, `sync`,
`devTeleport` (test rooms only); scheduled: `doRespawn`, `endRound`, `returnToLobby`, `detonate`,
`restorePickup`, `airdrop`, `hillTick`, `dropPlayer`; lifecycle: `onConnect`, `onDisconnect`.

**There is no server tick.** Instead of a loop running every 16 ms, everything timed is a one-shot
schedule (respawn in 5 s, round end, grenade fuse 1.5 s, pickup back in 20 s, lobby in 12 s, one hill
check a second in King of the Hill rounds) and everything else happens inside `sync`. This keeps the
server cheap and simple.

**Room lifecycle (state machine)**

```text
createRoom → LOBBY ──startRound──▶ PLAYING ──round_end_job──▶ ENDED ──lobby_job (12 s)──▶ LOBBY
                ▲                                               │  └─backToLobby (host)──▶ LOBBY
                └───────────────────────startRound (Play again)─┘
quickPlay → PLAYING ──round_end_job──▶ ENDED ──lobby_job (12 s)──▶ PLAYING (no lobby, next map)
last human leaves → room, pickups, jobs and its CPU players deleted
```

**Disconnects**: `onDisconnect` holds a human's slot for 30 seconds (`holdForReconnect`): the soldier
leaves the world, stats stay, and `drop_job` removes them if they do not return. Host passes at once
to the earliest-joined connected human. Any new connection from the same identity picks the slot back
up (`adoptConnection`), whether from a reload, an automatic reconnect or a reopened tab. A
connection-id check stops a late disconnect from removing the returning player. CPU players are
removed immediately.

**Progress**: `awardRound` runs at round end. It pays XP to connected humans (never in dev rooms) and
season points only when a second human is in the room. The token sits in `localStorage`, and a Web
Lock gives it to the first tab, so further tabs stay separate guests.

## 11. Game rules

**Modes**: Arms (pistol + chosen primary + knife + 2 frags), Blades (knife only, +15 % speed),
Boom (unlimited frags, max 3 live, knife backup), Snipers (sniper + knife).

**House rules (host)**: round 2/3/5/8/10 min; health 50/100/150/200; CPU skill;
infinite jetpack; infinite ammo; pickups on/off; airdrops on/off; acid on/off; Frenzy on/off; sudden
death on/off; deathmatch or King of the Hill; map or rotation; free-for-all or red vs blue; friendly
fire (teams only); floating grenades. Respawn is fixed at 5 s for everyone.
Every toggle starts **on**, so a fresh room is the fastest, most chaotic version; the host turns
off what the group does not want.

**Scoring**: kill +100; holding the hill +10 a second; killing a bounty (3-kill streak, glowing gold with a crown) +50 extra;
dying to acid or your own grenade −50; killing a teammate (friendly fire) −50 and no kill credit.
Leaderboard: score, then kills, then fewer deaths. Team match: the team with the higher total wins.

**Frenzy**: last 60 s: damage ×1.5, fuel refill ×2, red tint, faster music. Both client and server
compute it from the round end time; nothing extra is stored.

**Sudden death**: for the last 30 s the acid climbs from the floor to row 17. Like Frenzy it comes
from the round clock on both sides (`acidSurface`), so nothing is sent. Nobody spawns under it.

**King of the Hill**: one player (or team) alone in the zone scores +10 a second; two sides contest
it. The zone moves every 40 s, or early if the acid reaches it. `hillTick` runs once a second.

**Power-ups**: a shield (+50) takes weapon damage before HP; acid ignores it. An airdrop lands every
minute with a railgun: 150 damage, three shots, pierces bodies but not walls.

**Spawns** (`shared/spawn.ts`): drop spawns under the rising acid or within 200 px of where you died, rank the rest by
distance to the nearest living enemy (farthest first), pick randomly among the top 3. Round start
gives everyone distinct spawns; in team matches red starts on the left half, blue on the right.

**Pickups**: health +50 (capped at max HP), ammo refills the reserve, grenade crate +1 (max 3);
each returns 20 s after being taken (shields 30 s); only taken if useful.

**Teams**: balanced on join, players can switch, host can move anyone. Soldiers use the team
colour (red / blue), teammates carry a chevron above their name, the minimap always shows
teammates, and the score bar shows both team totals.

**Radar** (`render/radar.ts`): the minimap always shows you and teammates; an enemy appears only
for 3 s after they fire (shot, knife, grenade). An edge arrow points to an *off-screen* enemy who
just fired; enemies already on screen get no arrow, so it never covers them.

**Names**: if your callsign is empty or already used in the room, the server gives you a fresh
random one ("Volt Hawk"), so no two players look alike.

## 12. CPU players (`client/src/game/bot.ts`)

**How they connect**: each bot is a real client with its own SpacetimeDB connection and identity,
opened from the host's browser tab. It joins the room and plays through the same `sync` reducer
as a human, so the server checks bots exactly like people and the server needs no bot code.

**How they think** (a few rules per step, tuned per difficulty: Easy / Normal / Hard):

- notice only enemies within sight range (600–950 px) and in line of sight;
- re-read the target's position only every 0.15–0.45 s (delayed perception);
- wait 0.3–0.8 s reaction time before shooting; aim with a wandering error (0.07–0.26 rad);
  turn at a limited speed; fire in bursts with pauses;
- pick nearer targets more often, with randomness, avoiding players other bots already chase;
- keep a weapon-specific distance, strafe, hop, fly over walls and acid, hunt your last known
  position for a few seconds, then patrol between spawn points;
- in team matches, never target teammates.

Measured: against a player standing still at close range, Easy needs ~4–10 s, Normal ~4–20 s,
Hard ~2–4 s to kill them (an aimbot would need under 1 s).

## 13. User interface, mobile and touch controls

- DOM + CSS over the canvas; landscape-first layouts; phones detected by screen height ≤ 520 px.
  All menus are landscape-only on touch devices (a rotate prompt shows in portrait).
- The HUD updates the DOM only when a value changes; animations use only `transform` and
  `opacity` (cheap for the browser).
- **Twin sticks** (`ui/touch.ts`, Pointer Events, each finger tracked by id): both sticks rest at
  visible home positions and slide to wherever your thumb lands in that half of the screen.
  Left: horizontal runs, up is analog jetpack (0.15–0.3 ramps up to a hover, 0.3–0.55 is a
  wide hover band, beyond climbs), a firm straight pull down drops through platforms. Right: aims;
  past 55 % fires. Buttons (reload, swap, grenade, knife) sit on an arc around the right stick and
  hide when the mode doesn't use them.
- Fullscreen on start where supported, screen wake lock during matches, safe-area insets,
  installable web app manifest.
- **Emotes** (`emote_ev` event + Pixi sprites): eight Hinglish stickers behind the button beside
  the leaderboard (or `Q`). The picker drops down from the button, opens only when the player asks
  for it, and accepts a second finger while the sticks are held. The server echoes the emote to the
  room; clients draw it above the sender and follow them while they are alive. While dead, the emote
  stays at the exact death spot, where the camera is also held for the whole 5 s respawn. The local
  client draws its own emote immediately, then reconciles with the server echo.

## 14. Graphics and sound generated in code

- **Sprites**: drawn with Canvas 2D at load (soldier parts, weapons, effects, pickups with glow,
  icons) into one atlas. Map tiles are drawn with gradients, neon edges and details, then baked.
- **Sound** (`audio/audio.ts`): every sound is synthesised with `OfflineAudioContext`: filtered

  (Mini-Militia style), only for the local player.

## 16. Cheating: what the server checks and what it trusts

**Checked**: positions (inside the map, clear path, no wall crossings), speed against what physics
allows right now (`spendMove`: run and hop speed plus a fading bonus from real recoil, lunges and
blasts), a capped client clock, fire rate, ammo, weapon allowed in the mode, primary changes only
while dead, shot origin near the shooter, hit claims (range, line of sight to some part of the current
body, ray close to where the target was, pellets limited by the body's share of the cone, one body per
pellet), knife targets (server computes them), grenade counts and cooldowns, pickup touching, team
friendly-fire rule, host-only actions, kicked players can't rejoin, replayed packets, room and name
input, and rate limits per identity. All damage, scores and XP are computed on the server, and
locked stickers are refused.

**Trusted (known limits)**: the client chooses where to aim, so a modified client could aim
perfectly (an aimbot) within those checks. It also simulates its own jetpack fuel, so it can ignore
fuel in rooms with Infinite jetpack off, though speed and walls still apply. Every player's position
is sent to every client so it can be drawn, so a wallhack cannot be prevented. Identities are free, so
two accounts can farm each other slowly; the XP cap limits that. These are the usual trade-offs in
client-predicted shooters: full server physics would add latency to every key press.

## 19. The latency story: measurements and decisions

**What ping is**: the round-trip time for a message to reach the server and come back. It's
limited by distance (light in fibre covers ~200 km per millisecond, plus routing).

**Measured from the developer's laptop in India** (one round trip):

| Server | Round trip | Notes |
| --- | --- | --- |
| SpacetimeDB Maincloud (Leesburg, Virginia, USA) | ~245–305 ms | **the live server today** |
| Cloudflare Durable Object (via Singapore / Hong Kong / Tokyo) | 87–235 ms | measured with a test probe; not used |
| AWS Mumbai | ~67 ms | measured only; free for a limited period |
| Oracle Cloud Mumbai | ~38 ms | measured only; Always Free |
| Oracle Cloud Hyderabad | ~25 ms | measured only; Always Free |
| Same Wi-Fi (laptop as server, LAN mode) | ~2–10 ms | demo fallback |

**Decisions**

1. **Make the game behave well at high ping (done)**: client-side prediction, adaptive
   interpolation on the sender's timeline, client-timeline movement checks with an anti-cheat
   budget, lag-compensated hit checks with "cover wins". Result at ~250 ms real ping: 0
   snap-backs and no visible jumps in a hard-flying test.
2. **Move the server closer (prepared, not done yet)**: Cloudflare was measured but its free routing
   from this ISP leaves India, so latency was inconsistent. A self-hosted SpacetimeDB on Oracle
   Cloud's Always Free tier in Hyderabad/Mumbai would give ~25–40 ms with no code change. Until it
   is set up, the game runs on Maincloud at ~250 ms. Creating the account
   needs a person (card verification), so the steps are in `deploy/oracle/README.md` and the
   server setup is one script.
3. **Why not rewrite the server for Cloudflare?** It would replace a working, tested backend with
   a new one for a gain that depends on the ISP's routing (sometimes no gain at all), while the
   Indian VM gives a larger, consistent gain with zero code changes.

## 20. Known limitations and future work

- One server for everyone: players far from it get higher ping (region selection would fix it).
- Client-side aiming can't stop aimbots (needs server-side aim analysis).
- Progress lives on an anonymous identity, so clearing site data starts a player over.
- CPU players live in the host's tab: if the host closes the tab, the CPUs leave (in Quick Play the
  next host's tab adds new ones).
- Future: more maps, weapon alt-fires, grenade variants, a killcam, server regions, spectators,
  replays, voice/quick chat.

## 21. Viva questions and model answers

### General

**Q: What is your project?**
A real-time multiplayer jetpack shooter in the browser for up to 8 players, free-for-all or
teams, with CPU opponents. Client in TypeScript with PixiJS; server is a SpacetimeDB module; the
physics and rules code is shared by both.

**Q: Which lab requirements does it meet?**
Start screen, instructions, score, timer, lives/respawns, keyboard and touch controls, animation,
collision detection, scoring rules, difficulty progression (Frenzy, CPU skill), game states,
generated graphics/sound/music, collectibles, hazard, restart. See `docs/LAB_MAPPING.md`.

**Q: Why a web game?**
Nothing to install: anyone opens a link on a phone or laptop. It also forced us to handle real
networking, different screen sizes and touch input.

### Game loop, rendering, animation

**Q: What is a game loop? Why fixed timestep?**
A loop that updates and draws the game every frame. We update physics in fixed 1/60 s steps
using an accumulator, so the game plays the same at 30, 60 or 120 fps, and we interpolate the
drawing between steps so it still looks smooth.

**Q: How is animation done without sprite sheets?**
The soldier is built from parts (legs, torso, helmet, arm, gun, jetpack). Each frame we rotate
and offset them from the speed and aim: legs swing with a sine wave whose speed depends on
running speed, the arm rotates to the aim angle, the flame flickers between three textures.

**Q: How do you keep 60 fps on phones?**
One texture atlas so the GPU batches sprites, the map baked into six textures, object pools so
nothing is allocated per frame, DOM writes only on change, and a quality governor that lowers
resolution/effects if FPS drops.

**Q: What are WebGPU and WebGL?**
Browser APIs to use the graphics card. PixiJS tries WebGPU first and falls back to WebGL.

### Physics and collision

**Q: How does collision detection work?**
The player is an axis-aligned box. We move along X, check tiles the box overlaps, and push it
flush against a wall if needed; then the same for Y. Moving one axis at a time makes the response
simple and correct. Speeds are capped below half a tile per step so nothing tunnels through.

**Q: How do one-way platforms work?**
They only block when you're moving down and your feet were above the platform before the step.
Coming from below, your feet start below the top, so you pass through. Holding down ignores them.

**Q: Explain the jetpack physics.**
Thrust = 3000 × power, gravity = 1800, so power 0.6 hovers. While thrusting we damp vertical
speed (after gravity), so hovering is stable and you can fly sideways at one height. Fuel drains
while flying and refills on the ground.

**Q: Why not use a physics engine?**
We need simple platformer movement, not rigid-body physics, and the exact same deterministic code
on client and server. 200 lines we understand fully beat a large engine we'd have to tame.

### Shooting

**Q: How do bullets work?**
Guns are hitscan: each shot is a ray. A DDA walk through the tile grid finds the first wall; a
slab test finds which player hitbox the ray enters first before that wall.

**Q: Explain the DDA algorithm.**
From the start tile, compute the distance along the ray to the next vertical grid line and the
next horizontal grid line; step into whichever is closer; add the constant spacing for that axis;
repeat until a solid tile or max range. It visits exactly the tiles the ray crosses.

**Q: Explain the slab test.**
An axis-aligned box is the overlap of an x-band and a y-band. For each band compute the ray
distance where it enters and leaves. The ray hits the box if the largest entry distance is smaller
than the smallest exit distance (and positive, and before the wall).

**Q: How are grenades synchronised?**
We don't stream their position. The server stores the throw's start values; every client and the
server run the same deterministic simulation (fixed 120 Hz steps, only basic arithmetic), so they
compute identical paths and the blast happens where everyone saw it.

### Networking

**Q: Who decides if a hit happened?**
The shooter's client claims it; the server validates it (weapon, fire rate, ammo, range, line of
sight to the target's current position, ray close to where the target was) and computes the
damage. Hit markers appear only after the server confirms.

**Q: What is client-side prediction?**
Your own soldier moves immediately using the shared physics instead of waiting ~250 ms for the
server. The server corrects you only if it rejects a move.

**Q: What is interpolation and why draw other players in the past?**
Updates arrive ~20 times a second and unevenly. Drawing others a little in the past means there
are always two real snapshots to blend between, so motion is smooth. The delay adapts to each
player's measured lag and jitter.

**Q: What is lag compensation?**
The server remembers recent positions of every player. When checking a hit it uses where the
target was at the moment the shooter saw it, so a player with high ping who aimed correctly
still hits. We still require line of sight to the target's current position ("cover wins").

**Q: Why is your ping ~250 ms and what did you do about it?**
The managed server is in Virginia, USA; from India the round trip is ~250 ms. In code we made the
game smooth and fair at that ping (prediction, adaptive interpolation, client-timeline movement
checks, lag compensation). To lower ping itself we measured alternatives: Cloudflare 87–235 ms
(routes outside India), Oracle Cloud Hyderabad ~25 ms (Always Free). Today it still runs on
Maincloud at ~250 ms; moving to an Indian server is prepared (one setup script and a config
change) but needs an Oracle account, which a person has to create.

**Q: How does the client know the server time?**
NTP-style pings: RTT = now − sent; offset = serverTime − (sent + RTT/2); median of the last five.

**Q: What happens if two players shoot each other at the same time?**
Reducers run one at a time (each is a transaction), so whichever sync reaches the server first is
processed first. If it kills the other player, the second player's shots are ignored because
they're dead.

**Q: What happens if a player disconnects or reloads the page?**
On disconnect the server deletes their rows and hands host to the next human. On reload the
client rejoins the saved room code; a connection-id check stops the old connection's late
disconnect from removing them.

### Server and database

**Q: What is SpacetimeDB? Why use it?**
A database that runs server code. Tables hold the state, reducers change it as transactions,
clients subscribe and get changes pushed live, and scheduled tables give timers. It replaces a
separate game server, database and sync layer.

**Q: What is a reducer?**
A server function a client calls (like `sync` or `startRound`). It runs as a transaction: all its
changes commit together or none do. It can't return data; clients see the result through their
subscriptions.

**Q: What is a scheduled reducer? Why no game tick?**
A reducer that runs when a row in a schedule table says so. Respawns, round end, grenade fuses,
pickups and the lobby return are one-shot timers. Without a continuous tick the server only
works when something happens, which is cheaper and simpler.

**Q: What are event tables?**
Tables whose rows are broadcast to subscribers when the transaction commits and then discarded.
We use them for shots, hits, kills, explosions, pickups, pongs and kick notices.

**Q: Why split `player` and `pstate`?**
Position changes 20 times a second; stats change rarely. Separate tables mean a position update
doesn't resend the whole player row.

**Q: How is randomness handled on the server?**
Through `ctx.random`, which is deterministic inside the database. Shared code never uses
`Math.random()` or the wall clock, so client and server agree.

**Q: How are room codes made?**
Four letters from an alphabet without O, I and L (easily confused with 0 and 1), regenerated until
unique.

### Rules and features

**Q: How does difficulty progress?**
Frenzy in the last minute (×1.5 damage, ×2 fuel refill), bounty targets as streaks grow, CPU skill
levels, and host rules like health and mode. (Respawn is always 5 s.)

**Q: How do teams and friendly fire work?**
`room.teams` turns it on; each player has `team` 1 (red) or 2 (blue), balanced on join. With
friendly fire on, teammate hits count but a teamkill gives no kill and costs 50 points; with it
off, the server ignores teammate hits and the client lets bullets pass through teammates.

**Q: How does the spawn system avoid spawn camping?**
It drops spawns within 200 px of where you died, ranks the rest by distance from the nearest
living enemy, and picks randomly among the three farthest.

**Q: How does the radar avoid giving away hidden players?**
Enemies appear on the minimap only for 3 s after they fire, and edge arrows show only for
off-screen enemies who just fired. Hiding works until you shoot.

**Q: How do the CPU players work?**
Each is a real client with its own connection, run from the host's tab, playing through the same
validated `sync`. Its brain notices only visible enemies within range, perceives positions with a
delay, has reaction time, aim error, burst fire and limited turn speed, per difficulty.

### Assets, UI, audio

**Q: Did you use any downloaded assets?**
No art or sound files. Sprites are drawn with Canvas 2D at load; sounds and music are synthesised
with Web Audio. Only two open-licence fonts are bundled.

**Q: How do the touch controls work?**
Pointer Events track each finger. The left stick moves and controls analog jetpack power; the
right stick aims and fires when pushed past 55 %. Buttons around it do reload, swap, grenade and
knife, showing only when the mode uses them.

**Q: How does the game adapt to screen sizes?**
The camera keeps ~680 world px of height on laptops and zooms in on short phone screens; menus
have landscape layouts for phones; safe-area insets avoid notches.

**Q: How is sound made without files?**
`OfflineAudioContext` renders buffers at load: filtered white noise for gunshots, sine sweeps for
thumps, oscillators for music. A mixer pans sounds by position and limits to 16 voices.

### Code quality and data structures

**Q: Which data structures did you use?**
Maps (players by id), a ring buffer of typed arrays (snapshots), object pools (particles,
tracers), a 1D `Uint8Array` for the tile grid, arrays for position history on the server.

**Q: Time complexity of a shot?**
DDA is O(tiles crossed) (at most range/32 ≈ 75 for the sniper); the slab test is O(players) (≤ 8);
a shotgun repeats this for 7 pellets.

**Q: Where are the constants?**
`server/src/shared/config.ts` and `weapons.ts`. Changing a number changes it for client and
server.

**Q: How did you test it?**
46 unit tests for the simulation and validation, 7 Playwright suites that open several real
browsers and play full rounds (including a simulated 250 ms network), and strict type checking.

**Q: What was the hardest bug?**
High-ping smoothness. Fixed delays and server-clock movement checks worked locally (2 ms) but
caused snapping at 250 ms. We wrote a latency test that delays WebSocket messages with jitter,
reproduced it, and fixed it with sender-timeline timestamps, adaptive interpolation and
client-timeline movement checks with a time-debt cap.

**Q: What would you improve with more time?**
Server regions near players, more maps, server-side aim analysis against cheats, spectator mode.

## 23. Glossary

| Term | Meaning |
| --- | --- |
| Accumulator | Stores leftover frame time so physics steps stay a fixed size |
| AABB | Axis-aligned bounding box: a rectangle that doesn't rotate |
| Atlas | One big texture holding many small images |
| DDA | Digital differential analyzer: stepping through a grid along a ray |
| Deterministic | Same inputs always give exactly the same outputs |
| Event table | Rows broadcast once to subscribers, never stored |
| Hitscan | A shot that hits instantly along a ray (no travelling bullet) |
| Interpolation | Blending between two known states to draw smooth motion |
| Jitter | Variation in how late network messages arrive |
| Lag compensation | Judging a shot against where the target was when the shooter saw it |
| Ping / RTT | Round-trip time to the server and back |
| Prediction | Simulating your own movement locally before the server confirms |
| Reducer | A SpacetimeDB server function that changes tables as one transaction |
| Ring buffer | A fixed-size array reused in a circle for the latest N items |
| Scheduled reducer | A reducer run automatically at a given time |
| Slab test | Ray-vs-box test using the overlap of entry/exit distances per axis |
| Subscription | A client's live query; matching row changes are pushed to it |
| Transaction | A group of changes that all happen or none happen |
